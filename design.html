좋은 요구는 무엇을 측정하는지 명확하다. “빠르게 응답”보다 “동시 사용자 100명에서 95% 요청이 2초 이내 응답”이 검증하기 쉽다. 추적성 매트릭스는 요구를 설계·구현·테스트와 연결해 변경 영향을 확인한다.

과정으로 이해하기

  1. 회원은 주문을 취소할 수 있다 → 기능.
  2. 취소 요청은 2초 이내 처리한다 → 성능 비기능.
  3. 요구 R1을 테스트 T3에 연결 → 추적성.

응집도·결합도를 사례로 판단

기능 응집은 한 기능, 순차 응집은 앞 출력이 뒤 입력, 통신 응집은 같은 데이터, 절차 응집은 실행 순서, 시간 응집은 같은 시점, 논리 응집은 비슷한 종류, 우연 응집은 관련 없는 기능의 모음이다. 결합은 단순 자료 전달보다 제어 플래그·공유 전역·다른 모듈 내부 접근일수록 강하다.

SOLID를 위반 사례로 이해

SRP는 클래스가 변경되는 이유를 한 책임으로 모으는 원칙이다. OCP는 기존 안정 코드를 계속 수정하기보다 확장으로 새로운 동작을 넣도록 설계한다. LSP는 자식이 부모 계약을 지켜 대신 사용되어도 동작이 깨지지 않아야 한다.

ISP는 클라이언트가 쓰지 않는 메서드에 의존하지 않도록 인터페이스를 나누고 DIP는 고수준 정책과 저수준 구현이 구체 구현보다 추상에 의존하게 한다. 의존성 주입 DI는 필요한 의존 객체를 밖에서 제공하는 기법이다.

과정으로 이해하기

  1. 메일 전송과 급여 계산을 한 클래스에 섞음 → SRP 문제.
  2. 새 결제수단을 추가할 때 기존 분기문 수정이 누적 → OCP 관점 점검.
  3. 프린터가 스캔을 지원하지 않는데 스캔 메서드를 강제 → ISP 관점 점검.

MVC·계층·UI 설계와 서버 책임

MVC의 Model은 데이터·업무 규칙, View는 표시, Controller는 입력을 받아 흐름을 조정한다. 계층형은 화면·업무·데이터 접근처럼 책임을 층으로 나눈다. 파이프-필터는 독립 처리 단계를 연결하고 브로커는 중개자를 통해 분산 구성 요소를 연결한다.

UI 설계에서 와이어프레임은 배치 뼈대, 목업은 시각 형태, 프로토타입은 상호작용 검증, 스토리보드는 화면·이동·동작 설명이다. 서버에서 DTO는 계층 사이 전달 자료, DAO는 데이터 접근, 서비스는 업무 규칙을 담당하는 관용적 구분이다.

과정으로 이해하기

  1. 주문 요청을 Controller가 받고 Service가 재고·결제를 판단, DAO가 저장소에 접근.
  2. View는 결과를 표시하고 업무 규칙을 화면마다 중복 구현하지 않는다.
