01

요구사항과 개발 모형

기능 요구는 무엇을 하는가, 비기능 요구는 성능·보안·신뢰성 등 어떤 수준으로 동작하는가다. 도출 → 분석 → 명세 → 확인의 흐름으로 이해한다. 폭포수는 단계 순차, 프로토타입은 시제품 피드백, 나선형은 위험 분석의 반복이다.

꼭 기억할 것

애자일은 짧은 반복과 피드백. 스크럼의 제품 백로그·스프린트 백로그·스프린트·회고를 구별한다.

헷갈리는 지점 “2초 이내 응답”은 비기능 요구. “주문을 취소한다”는 기능 요구다.

02

UML 관계와 다이어그램

클래스·객체·컴포넌트·배치·패키지는 구조 표현, 유스케이스·활동·상태·시퀀스는 행위 표현이다. 시퀀스는 시간 순 메시지, 상태는 이벤트에 따른 상태 전이다.

꼭 기억할 것

일반화는 상속, 실체화는 인터페이스 구현, 연관은 연결, 의존은 사용. 집합은 빈 마름모, 합성은 찬 마름모를 전체 쪽에 표시한다.

헷갈리는 지점 합성은 강한 소유 관계다. 화살표의 방향과 마름모가 있는 쪽을 뒤바꾸지 않는다.

03

응집도와 결합도

응집도는 한 모듈 안의 관련성으로 높을수록 좋다. 강→약: 기능→순차→교환(통신)→절차→시간→논리→우연. 결합도는 모듈 사이 의존으로 낮을수록 좋다. 강→약: 내용→공통→외부→제어→스탬프→자료.

꼭 기억할 것

순차 응집은 앞 출력이 뒤 입력, 교환 응집은 같은 자료 사용. 스탬프 결합은 구조 전체 전달, 자료 결합은 필요한 자료 전달.

헷갈리는 지점 외부 결합은 외부 형식·프로토콜·장치 의존, 공통 결합은 공통 전역자료 공유, 내용 결합은 내부 구현 직접 참조·수정이다.

04

객체지향과 SOLID

캡슐화는 상태와 동작 묶기·접근 통제, 추상화는 핵심 모델링, 상속은 기존 특성 확장, 다형성은 같은 메시지에 다른 구현이다. SRP 단일 책임, OCP 확장에 열리고 수정에 닫힘, LSP 대체 가능, ISP 인터페이스 분리, DIP 추상에 의존.

꼭 기억할 것

DIP는 고수준 정책이 저수준 구현의 구체 클래스에 직접 묶이지 않도록 추상에 의존한다.

헷갈리는 지점 의존성 주입 DI는 DIP 구현을 도울 수 있는 기법이지 같은 용어가 아니다.

05

생성 패턴 5개

Singleton은 하나의 인스턴스 접근, Factory Method는 생성할 객체 결정을 하위 구현에 위임, Abstract Factory는 관련 제품군 생성, Builder는 복잡한 객체 조립 단계 분리, Prototype은 기존 객체 복제다.

꼭 기억할 것

“관련 객체들의 제품군” → Abstract Factory. “복잡한 생성 순서” → Builder.

헷갈리는 지점 Singleton이 자동으로 스레드 안전을 보장하지는 않는다. Factory Method와 Abstract Factory의 초점을 구별한다.

06

구조 패턴 7개

Adapter 인터페이스 변환, Bridge 추상과 구현의 독립 확장, Composite 부분-전체 트리의 동일 취급, Decorator 객체 감싸 기능 추가, Facade 복잡한 내부에 단순한 창구, Flyweight 공유로 비용 절감, Proxy 대리 접근·통제.

꼭 기억할 것

“호환되지 않는 API 연결” Adapter / “추상·구현 계층 분리” Bridge / “대리인” Proxy.

헷갈리는 지점 Decorator는 기능 추가, Proxy는 접근·생명주기 등 대리 제어에 초점. 모양이 비슷해도 목적이 다르다.

07

행위 패턴 11개

Observer 상태 변화 알림, Strategy 교체 가능한 알고리즘, State 상태별 행동, Template Method 처리 뼈대와 세부 단계, Command 요청을 객체화, Iterator 순차 접근, Mediator 상호작용 중재, Memento 상태 보관·복원, Visitor 연산 분리, Chain of Responsibility 처리자 연결, Interpreter 문법 해석.

꼭 기억할 것

옵저버는 발행자와 구독자, 전략은 정렬·결제 방식 교체, 상태는 상태 변화에 따른 동작 변화로 떠올린다.

헷갈리는 지점 Strategy와 State를 구별할 때 “선택한 알고리즘 교체”인지 “객체 내부 상태에 따른 행동”인지 본다.

08

UI와 아키텍처

UI 원칙은 직관성·유효성·학습성·유연성으로 정리한다. 와이어프레임은 화면 뼈대, 스토리보드는 화면 흐름과 설명, 프로토타입은 동작 검증용 모형이다. MVC는 데이터·화면·입력 제어 책임을 나눈다.

꼭 기억할 것

계층형은 책임별 층, 클라이언트-서버는 요청·서비스 분리, 파이프-필터는 처리 단계의 흐름.

헷갈리는 지점 UI는 접점, UX는 이용 경험 전체다. 시각 디자인만으로 UX를 정의하지 않는다.

09

이벤트 기반 아키텍처와 CQRS

이벤트 기반 아키텍처는 상태 변화를 이벤트로 발행하고, 관심 있는 구성요소가 이를 구독해 비동기로 반응하는 구조다. CQRS(명령과 조회의 책임 분리)는 데이터를 변경하는 명령과 데이터를 조회하는 질의의 모델을 분리해 서로 다른 최적화를 적용한다.

꼭 기억할 것

이벤트 기반 구조는 발행자와 구독자를 느슨하게 결합해 확장에 유리하지만 전체 흐름 추적이 어려워질 수 있다.

헷갈리는 지점 CQRS가 항상 별도의 데이터베이스를 요구하는 것은 아니다. 명령과 조회의 책임을 분리하는 것이 핵심이다.

직접 풀어보기 10문제

모두 유형 연습을 위해 직접 만든 문제입니다. C 예제의 printf·strlen은 필요한 표준 헤더가 포함된 상황을 가정합니다. Java는 표시된 클래스·main 위치에서 실행합니다. 단답은 동의어가 있을 수 있어 자동 판정 대신 자기 채점을 사용합니다.
